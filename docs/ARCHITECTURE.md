# Architecture

## Shape

```
 Browser (team)            Browser (public)
      │                         │
 app.axerealty.lk          axerealty.lk            ← two Vercel projects, one repo
      │                         │
      └────── Next.js (App Router, TypeScript) ─────┐
                   │ publishable key + user JWT     │ secret key (server only:
                   ▼                                │  jobs, migration, website reads)
          Supabase Postgres  ◄──────────────────────┘
          • row-level security on every table
          • triggers: IDs, audit log, stamps, guards
          • Supabase Auth (email + password, TOTP 2FA)
```

## Decisions

| Area | Choice | Why |
| --- | --- | --- |
| Data access | `supabase-js` with the user's session; SQL migrations are the source of truth | Every query from the app runs as the signed-in user, so row-level security applies automatically. An ORM connecting as the database owner (Drizzle/Prisma) would bypass RLS unless every query switched role, which is easy to get wrong. This replaces the earlier Drizzle plan. Typed queries come from `npm run db:types`. |
| Permissions | `role_permissions` table + `app.can(table, action)` in every policy | Adding a role (e.g. Sales Manager) or widening one is a data change, not code. |
| 2FA | A Super Admin session without 2FA (`aal2`) gets no rows at all | Enforced in the database, so a stolen password alone can't reach closings. |
| Soft delete | `deleted_at` on every main table; only roles with delete rights may set or clear it | Super Admin can restore anything. |
| Audit | One trigger on every table writes before/after JSON to `audit_log` | Nothing bypasses it, including server jobs (source = job / migration). |
| IDs | Listing No and Lead ID generated by trigger at insert, then frozen | Fixes the Airtable bug where every code changes on 1 January. |
| Money tables | Closings, receipts, payouts, schedules, targets: Super Admin only (Sales Manager read-only, future) | SPEC 5.1. Tested in `tests/db/security.test.ts`. |
| Public website | `anon` has no table access at all | Phase 1 adds an allow-list view of public listing fields only. |
| Commission schedules | Versioned rows; a schedule with closings against it can't be edited | Forward-only rule (SPEC 7.9). |

## Environments

| Environment | Supabase project | Vercel | Who |
| --- | --- | --- | --- |
| Local | staging | `npm run dev` | developer |
| Staging | `axe-staging` | preview deployments | Adhith approves here |
| Production | `axe-production` | production (`main`) | the team |

Vercel environment variables: the three Supabase values exist twice, once for **Production**
(axe-production) and once for **All Pre-Production Environments** (axe-staging). `NEXT_PUBLIC_*`
values are type Config (they are public by design); `SUPABASE_SECRET_KEY` and `CRON_SECRET` are Secret.
`NEXT_PUBLIC_*` values are built into the app, so a settings change needs a new deployment.

## Schemas

- `public` — business tables (exposed through the Supabase API, guarded by RLS)
- `app` — helper functions used by policies and triggers (not exposed)
- `auth` — Supabase Auth (managed by Supabase)

## Trigger order on a table

`t10_stamp` → `t20_soft_delete` → `t30_ids` → `t40_admin_fields` → `t50_guard_used` (before) → row written → `t60_*` history → `z90_audit` (after).
